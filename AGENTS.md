# Task Manager

Небольшое тестовое приложение для управления списками и задачами. Приоритет — работающие сценарии задания, понятный код, тесты и опубликованное demo. Добавлять структуру вместе с первой реальной функцией.

## Стек и команды

- Next.js App Router, React, TypeScript, Ant Design, Vitest, Storybook и pnpm.
- Актуальные версии и команды находятся в `package.json`; использовать pnpm и сохранять lockfile.
- Запуск: `pnpm dev`, Storybook: `pnpm storybook`.
- Проверки: `pnpm format:check`, `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm build-storybook`.
- Автоисправления выполнять явно через `pnpm format` и `pnpm lint:fix`.

## Завершение этапа и Git

- Этап — завершённая согласованная порция изменений. Объяснения, вопросы и промежуточные правки сами по себе не требуют коммита.
- После каждого этапа проводить ревью своего diff: проверять требования задания, корректность поведения, архитектуру, обработку ошибок и возможные регрессии. Исправлять найденные проблемы до коммита.
- Для ревью кода использовать локальный skill [task-manager-code-review](.agents/skills/task-manager-code-review/SKILL.md), который описывает предметные проверки и формат замечаний.
- Выполнять проверки, соответствующие изменению, по правилам раздела «UI и проверки». Успешный запуск тестов не заменяет ревью кода.
- После успешного ревью и проверок создавать отдельный содержательный коммит и выполнять push текущей ветки в origin, если пользователь явно не попросил отложить коммит или push. Включать в коммит только изменения текущего этапа, сохраняя посторонние правки.
- В итоговом сообщении кратко указывать результат ревью, выполненные проверки, хеш коммита и результат push. Если проверка или push не удались, сообщать об этом явно.

## Архитектура frontend

- Облегчённый FSD: `app -> views -> widgets -> features -> entities -> shared`. Импортировать код нижележащих слоёв; не создавать все слои заранее.
- `app` содержит маршруты, layouts, providers и глобальные стили. `page.tsx` должен оставаться тонким; полноценный экран собирать в конкретном view.
- `views` компонует экраны, `widgets` — самостоятельные крупные блоки, `features` — действия пользователя, `entities` — бизнес-сущности и их логику, `shared` — общий технический код.
- Перед созданием helper или UI-компонента проверять существующие реализации. Предметную логику задач не переносить в `shared` ради переиспользования.
- Использовать `@/*` для импортов из `src`. Между slices обращаться через их публичный API; не создавать общий barrel всех views.
- Серверные действия feature размещать в `api/actions.ts`, публичный серверный вход — `api/index.ts`. Корневой `index.ts` feature оставлять для UI и общих типов.
- По умолчанию сохранять серверные компоненты. `use client` ставить рядом с интерактивным кодом.
- Истории `*.stories.tsx` и тесты `*.test.ts` размещать рядом с соответствующим кодом. `src/stories/antd.stories.tsx` — проверка инфраструктуры, а не образец расположения продуктовых историй.

## Данные и сервер

- Чтение — через серверные компоненты и слой данных, изменения — через Server Actions. Массивы в UI-состоянии не являются источником бизнес-данных.
- `src/server` — отдельная серверная часть: подключение к базе, сессии, чтение и запись данных. Она находится вне цепочки frontend-слоёв.
- Прямой доступ к базе и секретам защищать через `server-only`. Клиентский код обращается к серверным действиям, а не к базе.
- В каждой защищённой серверной операции проверять сессию и входные данные. Проверки страницы и клиентской формы не заменяют серверные проверки.
- Локальное состояние модалок, полей и фильтров хранить рядом с интерфейсом.
- TanStack Query, глобальное хранилище и отдельный backend добавлять только при конкретной необходимости.
- Секреты и строки подключения хранить в переменных окружения; не включать их в репозиторий или клиентский bundle.

## UI и проверки

- Использовать существующие Ant Design providers и тему. В приложении должен быть один корневой `AntdRegistry`.
- Для форм использовать валидацию Ant Design; учитывать загрузку, ошибки, пустые состояния и повторную отправку.
- Сортировку и расчёт показателей держать отдельно от компонентов и проверять юнит-тестами с фиксированным временем.
- По заданию нужны минимум 8 юнит-тестов сортировки/счётчиков и 5 продуктовых историй с `play`, включая вход, валидацию и смену статуса.
- В установленном Storybook использовать `storybook/test`; причины отличия от имени пакета в ТЗ описаны в `docs/decisions.md`.
- Выполнять проверки, соответствующие изменению. Для изменений документации достаточно проверки форматирования; для кода — линтер, типы, затронутые тесты и соответствующая сборка.
