# Task Manager

Тестовое задание для Middle Frontend-разработчика: приложение для управления списками и задачами.

[GitHub-репозиторий](https://github.com/AlexCherem/task-manager). Архитектурные решения описаны в [документе решений](docs/decisions.md).

## Demo

Live demo пока не опубликовано. Перед сдачей нужно разместить приложение на Vercel и добавить сюда его URL. Проверочная учётная запись: `admin@example.com` / `Admin123!`.

## Запуск

Требуются Node.js 22 (не ниже 22.12.0) и pnpm 11.19.0. Версии закреплены в `engines.node` и `packageManager` файла `package.json`.

```bash
pnpm install
cp .env.example .env.local
```

Перед запуском заполните в `.env.local` обе переменные:

- `SESSION_SECRET` — случайная строка длиной не менее 32 символов; сгенерировать можно командой `openssl rand -hex 32`.
- `DATABASE_URL` — строка подключения к PostgreSQL в Neon; подробнее ниже.

Реальные значения не коммитятся. Затем подготовьте таблицы и запустите приложение:

```bash
pnpm db:setup
pnpm dev
```

При публикации задайте `DATABASE_URL` и отдельный `SESSION_SECRET` в переменных окружения Vercel.

Откройте адрес из вывода терминала: обычно http://localhost:3000. Если порт занят, Next.js выберет следующий свободный.

## Настройки сборки Vercel

При импорте репозитория используйте следующие настройки:

- Framework Preset — `Next.js`, Root Directory — `./`.
- Build Command — `pnpm build`; Install Command и Output Directory оставьте автоматическими.
- `DATABASE_URL` — строка подключения к существующей базе Neon.
- `SESSION_SECRET` — отдельный случайный ключ длиной не менее 32 символов.
- `ENABLE_EXPERIMENTAL_COREPACK=1` — переменная окружения для использования `pnpm@11.19.0` из `packageManager`, согласно [документации Vercel](https://vercel.com/docs/builds/configure-a-build#corepack).

Задайте переменные для окружения Production, а при использовании preview-развёртываний — и для Preview. Диапазон `engines.node` ограничивает Node.js веткой 22. База уже подготовлена отдельно; `pnpm build` не применяет SQL-схему.

## Подключение PostgreSQL

В Neon создайте проект и скопируйте прямую строку подключения из окна Connect в `DATABASE_URL` файла `.env.local`. Шаблон переменной есть в `.env.example`. При публикации задайте её в переменных окружения Vercel.

Серверный модуль `src/server/db.ts` предоставляет `getDb()`: он читает `DATABASE_URL` и создаёт функцию для SQL-запросов через официальный `@neondatabase/serverless`. Драйвер выполняет запросы по HTTPS. Модуль защищён через `server-only`; проверку сессии и входных данных выполняют использующие его операции слоя данных.

Проверить реальное соединение:

```bash
pnpm db:check
```

Команда загружает `.env.local` и выполняет `SELECT 1` через тот же `getDb()`. Она не создаёт таблицы и не меняет данные. Скрипт запускается в Node.js с поддержкой импорта TypeScript и условием `react-server` для серверного модуля; Next.js для него запускать не требуется. Адрес подключения и пароль не выводятся. Проверка соединения выполняется отдельно от юнит- и Storybook-тестов.

## Схема и серверные функции списков

После настройки `DATABASE_URL` подготовьте таблицы:

```bash
pnpm db:setup
```

SQL-файлы `db/schema/*.sql` выполняются по имени в одной транзакции; каждый файл содержит одну SQL-команду. Это начальная инициализация схемы: повторный запуск сохраняет существующие таблицы и записи благодаря `IF NOT EXISTS`. Изменения уже существующих колонок и ограничений нужно оформлять отдельными миграциями, а не редактированием начальной схемы.

`task_lists` хранит название списка (до 100 символов), UUID и дату создания. `tasks` хранит поля модели задачи, обязательный конечный дедлайн и ссылку на список. Статусы и приоритеты ограничены допустимыми значениями. Удаление списка удаляет его задачи через внешний ключ `ON DELETE CASCADE`.

В `src/server/lists` доступны `getTaskLists(search?)`, `createTaskList(title)`, `renameTaskList(id, title)` и `deleteTaskList(id)`. Все функции проверяют сессию. Чтение сортирует списки по дате создания и UUID по убыванию. Поиск проверяет вхождение части названия без учёта регистра; пробелы по краям запроса обрезаются, пустой запрос возвращает все списки. Символы `%`, `_` и обратный слеш считаются обычным текстом. Создание обрезает пробелы, проверяет название и возвращает список либо ошибку валидации; технические ошибки поднимаются к вызывающему коду. SQL использует параметры. Единственная демо-учётная запись работает с общим набором списков.

Проверить функции и ограничения на настоящей базе:

```bash
pnpm test:database
```

Эти тесты используют `DATABASE_URL` из `.env.local` и удаляют только собственные тестовые записи. Проверка сессии в интеграционных тестах заменена mock, SQL и PostgreSQL работают реально. Отказ при отсутствии сессии и валидация дополнительно покрыты юнит-тестами. Обычный `pnpm test` запускает только юнит- и Storybook-тесты без подключения к базе.

Страница `/lists` читает сохранённые списки серверной функцией. Кнопка «Создать список» открывает форму Ant Design; после успешного Server Action выполняется `revalidatePath('/lists')`, и новая карточка появляется без ручной перезагрузки. Форма показывает валидацию, загрузку и ошибки, очищается после отмены или успеха. Кнопка «Переименовать» на карточке открывает форму с текущим названием. Сохранение проверяет UUID и название на сервере, обновляет только выбранный список и повторно валидирует `/lists`. Если список уже удалён, форма показывает понятную ошибку. Кнопка «Удалить» открывает подтверждение с названием списка и предупреждением об удалении всех его задач без восстановления. После подтверждения сервер проверяет сессию и UUID, выполняет DELETE с каскадом задач и обновляет `/lists`. Повторное удаление отсутствующего списка считается успешным. Поле поиска отправляет GET-форму Next.js на `/lists?q=...` по кнопке «Найти» или Enter. Запрос хранится в URL и сохраняется после перезагрузки; кнопка «Сбросить» очищает поле и возвращает все списки. Она всегда видна и отключена, когда поле пустое. При активном поиске показано количество найденных списков и отдельное пустое состояние. Создание, переименование и удаление обновляют выдачу с учётом текущего запроса. Название карточки открывает `/lists/[id]`. Карточки показывают общее количество задач, счётчики новых, выполняемых, выполненных и просроченных задач, а также процент выполнения. Красный индикатор означает наличие просрочки; жёлтый — дедлайн незавершённой задачи в ближайшие 48 часов при отсутствии просрочки. Пустой список имеет нулевые показатели. Просрочка учитывается дополнительно к основному статусу, поэтому четыре счётчика не нужно складывать.

## Задачи списка

Страница `/lists/[id]` загружает список и его задачи из PostgreSQL. Неверный UUID или отсутствующий список показывают страницу «Список не найден». Таблица содержит название и описание, статус, приоритет и дедлайн; использует `sortTasks`, отмечает незавершённые просроченные задачи и показывает по 10 строк на странице.

«Создать задачу» открывает форму с обязательными названием и дедлайном. Описание необязательно; начальные значения — «Новая» и «Средний». Дату и время можно выбрать в русифицированном DatePicker Ant Design или ввести вручную. Значение переводится из местного времени браузера в UTC перед отправкой. Сервер проверяет все поля повторно, принимает конечный корректный ISO timestamp в UTC и сохраняет задачу только в существующий список. Прошедшие дедлайны разрешены. После сохранения таблица и количество задач обновляются через `revalidatePath`; перезагрузка читает сохранённые данные.

В `src/server/tasks` находятся `getTasksByList(listId)`, `getTaskListStats(listIds)`, `createTask(input)`, `updateTask(input)` и `deleteTask(input)`. Все операции проверяют сессию. Создание использует один параметризованный `INSERT ... SELECT` из существующего списка; внешний ключ не позволяет создать задачу без родителя. Технические ошибки не превращаются в успешный результат, ожидаемые ошибки отображаются в форме.

Клик по названию задачи открывает модальное окно редактирования со всеми сохранёнными полями. Отмена не сохраняет черновик; повторное открытие использует актуальные данные таблицы. Сервер повторно проверяет поля, сессию, UUID задачи и её принадлежность списку. После сохранения обновляются таблица, сортировка, счётчики и прогресс списка. При ошибке форма остаётся открытой с введёнными значениями и позволяет повторить отправку.

В последней колонке «Действия» находится кнопка «Удалить» каждой задачи. Подтверждение показывает название и предупреждает, что восстановление невозможно. Отмена не отправляет запрос. Во время удаления подтверждение и закрытие заблокированы; ошибка остаётся в окне и позволяет повторить попытку. Сервер проверяет сессию и оба UUID, удаляет только совпадение задачи и списка. Повторное удаление отсутствующей задачи успешно. После удаления обновляются таблица и показатели `/lists`; при удалении последней задачи показано пустое состояние. На узком экране колонка доступна горизонтальной прокруткой таблицы.

Над таблицей расположены фильтры по статусу и приоритету и флажок «Только просроченные». Все выбранные условия действуют одновременно. Выполненные задачи не считаются просроченными. Сброс всегда виден и отключён без активных фильтров. Счётчик «Показано задач» относится к отфильтрованным строкам, а общий счётчик списка и показатели карточек — ко всем задачам. При изменении фильтров таблица возвращается на первую страницу и сохраняет сортировку. Пустой список и отсутствие совпадений имеют разные сообщения. Фильтры локальны для открытого списка и сбрасываются при перезагрузке страницы; источник задач — PostgreSQL.

## Вход

- Страница входа: `/login`. Главная страница перенаправляет на `/lists`, а без сессии — на `/login`.
- Проверочная учётная запись: `admin@example.com` / `Admin123!`. Регистрация не предусмотрена заданием.
- Данные проверяются серверным действием; пароль не передаётся в cookie. Подписанная через `jose` сессия хранится 8 часов в HttpOnly cookie с SameSite=Lax и Secure в production.
- `/lists` проверяет подпись и срок действия сессии перед отображением. Страница отображает сохранённые списки и формы создания, переименования и удаления; общий хедер показывает пользователя, переключатель темы и кнопку выхода.
- После выхода cookie удаляется, а доступ к `/lists` снова требует входа. Серверные операции со списками и задачами также самостоятельно проверяют сессию.

## Ant Design

Корневой layout подключает `AppProviders` из `src/app/providers`. Он собирает один `AntdRegistry` для серверных стилей, `ThemeProvider` для выбора темы и `AntdProvider` для русской локализации, темы и контекста Ant Design.

Токены темы находятся в `src/shared/config/antd.ts`. Storybook использует тот же `AppProviders`, что и приложение.

## Тема и хедер

На рабочих страницах общий хедер содержит ссылку на списки, email пользователя, выход и переключатель «Светлая / Тёмная / Системная». Он подключён в layout группы `(workspace)`.

По умолчанию используется системная тема. `next-themes` сохраняет выбор в localStorage под ключом `task-manager-theme` и отслеживает изменения темы ОС в системном режиме. Ant Design переключается между `defaultAlgorithm` и `darkAlgorithm`; фон и собственные стили используют CSS-переменные. Выбранная тема применяется и к странице входа.

## Vitest и Storybook

В Vitest настроены три проекта:

- `unit` — юнит-тесты бизнес-логики в файлах `src/**/*.test.ts`, среда Node.js.
- `storybook` — истории компонентов и их `play`-сценарии в Chromium через Playwright.
- `database` — отдельные интеграционные тесты серверных функций и ограничений PostgreSQL, запускаются через `pnpm test:database`.

```bash
pnpm test                  # юнит- и Storybook-тесты, один прогон
pnpm test:watch            # наблюдение за изменениями
pnpm test:unit             # только юнит-тесты
pnpm test:storybook        # только истории и interaction tests
pnpm storybook            # Storybook на http://localhost:6006
pnpm build-storybook      # статическая сборка в storybook-static
```

История `UI/Ant Design` проверяет инфраструктуру. Продуктовые истории `Features/Auth/LoginForm` проверяют отправку формы, обязательные поля, некорректный email, ошибку учётных данных, сетевую ошибку, повторную отправку и блокировку полей во время запроса. В Storybook обработчик входа заменяется контролируемой функцией; реальные cookie проверяются в приложении. История `Features/Theme/ThemeSwitcher` проверяет выбор трёх режимов, применённую тему и сохранение настройки. Истории `Widgets/Tasks/TaskListTasks` проверяют смену статуса существующей задачи, обновление таблицы и сортировки, редактирование полей, валидацию, отмену, ошибки и блокировку отправки. Mock имитирует новые серверные props; реальное сохранение и пересчёт статистики проверяются на PostgreSQL.

Юнит-тесты модели задач проверяют сортировку, счётчики, прогресс, преимущество просрочки и границы интервала 48 часов. Время передаётся в функции явно и зафиксировано в тестах. Запуск: `pnpm test:unit`.

В задании указан пакет `@storybook/test`. В установленном Storybook 10 его функции доступны через `storybook/test`: именно оттуда импортируются `expect`, `fn` и инструменты взаимодействия. Используем актуальный API, описанный в [документации Storybook](https://storybook.js.org/docs/writing-tests/interaction-testing).

- `src/app/(workspace)/layout.tsx` — проверка сессии и общий каркас рабочих страниц.
- `src/widgets/app-header` — общий хедер.
- `src/features/theme` — переключатель темы и его история.
- `src/features/create-list` — модальное окно создания списка, Server Action и пять interaction-историй.
- `src/features/filter-tasks` — фильтры статуса, приоритета и просрочки со сбросом.
- `src/features/delete-task` — кнопка удаления задачи с подтверждением, Server Action и interaction-истории.
- `src/features/edit-task` — модальное окно редактирования и Server Action.
- `src/widgets/task-list-tasks` — таблица с выбором задачи, модальным окном и interaction-историями.
- `src/features/create-task` — форма создания задачи, Server Action и шесть interaction-историй.
- `src/features/search-lists` — форма поиска по названию через URL и interaction-истории.
- `src/features/delete-list` — подтверждение удаления списка вместе с задачами, Server Action и interaction-истории.
- `src/features/rename-list` — переименование списка, Server Action и interaction-истории.
- `src/views/login`, `src/views/lists` и `src/views/task-list` — композиция экранов.
- `src/features/auth` — форма, её типы, истории и Server Actions входа/выхода. `api/actions.ts` содержит серверные действия; публичный серверный вход — `api/index.ts`.
- `src/server/auth/session.ts` — проверочная учётная запись, подпись и проверка сессии, cookie.
- `src/server/tasks` — чтение, создание, редактирование, удаление и статистика задач с серверной валидацией, юнит- и интеграционные тесты.
- `src/server/db.ts` — серверный клиент PostgreSQL через драйвер Neon.
- `src/server/lists` — чтение с поиском, создание, переименование и удаление списков, юнит- и интеграционные тесты.
- `src/entities/task-list` — тип списка, общий результат изменения и ограничение названия.
- `db/schema` и `scripts/setup-db.mjs` — начальная SQL-схема и её применение.
- `scripts/check-db.mjs` — проверка подключения командой `pnpm db:check`.
- `src/app/globals.css` — общие стили и оформление начальной страницы.
- `src/shared/ui/button` — общая кнопка над Ant Design: стандартные props и ref, блокировка и aria-busy во время загрузки, Storybook-сценарии.
- `src/shared/config/antd.ts` — типизированная тема Ant Design.
- `src/entities/task` — модель задачи, функции `sortTasks` и `getTaskStats`, типы операций, подписи статусов и приоритетов. Отдельный UI-вход `entities/task/ui` предоставляет таблицу, показатели и общие поля формы, чтобы серверный код не импортировал компоненты Ant Design.
- `src/stories/antd.stories.tsx` — проверочная история с `play`.
- `.storybook` — настройки Storybook и общего окружения тестов.
- `vitest.config.ts` — конфигурация юнит- и браузерных тестов.
- `@/*` — сокращённый путь к файлам внутри `src`.

Функциональность ТЗ реализована и проверена локально. Оставшийся пункт сдачи — публикация live demo и проверка опубликованного приложения.
