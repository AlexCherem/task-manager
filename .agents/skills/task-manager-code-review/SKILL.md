# Ревью кода Task Manager

Ищи подтверждённые ошибки и регрессии в пользовательском сценарии. Учитывай [AGENTS.md](../../../AGENTS.md); правила коммита и push находятся там.

## Границы ревью

- Определи проверяемый diff: локальные изменения либо явно выбранные base/head. Сначала прочитай изменённые файлы, затем связанный код, необходимый для проверки поведения.
- Проверяй изменения и их последствия, сохраняя согласованный объём этапа. Не превращай небольшой diff в аудит всего приложения или формальную перестройку FSD.
- Если пользователь просит только ревью, не редактируй файлы, не запускай автоисправления, не меняй данные или схему базы и не выполняй commit/push. В рамках реализации используй замечания для исправления текущего этапа по правилам AGENTS.md.

## Серверные операции и данные

- Проследи путь от формы или страницы до Server Action, серверных функций и PostgreSQL. Проверь серверную валидацию внешних значений и проверку сессии перед защищённым чтением или записью; проверка layout не заменяет защиту операции.
- Убедись, что приватные серверные модули и секреты не попадают в клиентские импорты или возвращаемые данные. Проверь границы Server/Client Components по AGENTS.md.
- Проверь параметризацию SQL. Значения пользователя должны передаваться параметрами или интерполяцией tagged template драйвера, а не конкатенацией SQL-строк; raw/unsafe-фрагменты требуют доверенного источника.
- Для зависимых записей проверь атомарность. При изменениях схемы или удаления проверь ограничения, связи, влияние на существующие данные и воспроизводимый способ применения изменений.
- Убедись, что общий catch не превращает служебные сигналы Next.js, например redirect или notFound, в обычную ошибку формы. Ожидаемые ошибки должны давать понятный результат без раскрытия внутренностей базы.
- После мутации проверь обновление затронутых данных: карточек, списка задач, счётчиков и прогресса. Перезагрузка страницы должна читать сохранённые данные; успешный mock формы этого не доказывает.

## Доменные правила и интерфейс

- При изменениях сортировки, счётчиков и дат сверяй [решения проекта](../../../docs/decisions.md) и существующую модель задач. Проверяй границы времени, часовые пояса и соотношение основного статуса с признаком просрочки; используй существующую доменную логику вместо параллельного расчёта.
- Для затронутой формы пройди успешную отправку, валидацию, ошибку и повторную попытку. Проверь блокировку повторной отправки, отмену и повторное открытие, очистку устаревших ошибок и значений.
- Проверь loading/error/empty-состояния, подписи элементов управления и стабильные идентификаторы строк. Сверяй чтение и редактирование одного объекта, чтобы UI не показывал устаревшее состояние как актуальное.
- Если изменены тема или стили, проверь затронутый экран в светлой и тёмной теме и на узком экране. Для изменений переключателя дополнительно проверь system и сохранение выбора после перезагрузки.

## Проверки и результат

- Выбирай проверки по изменению и AGENTS.md. Существующий успешный прогон используй, пока код не изменился и не появились новые основания для повторения.
- В Storybook play проверяй наблюдаемый результат через assertions. Различай проверку UI с mock и реальное сохранение, авторизацию или переход в приложении.
- Отличай ошибки изменения от ранее существующих проблем. Не выдавай непроверенное поведение за подтверждённое.
- Сообщай доказуемые замечания по убыванию серьёзности: приоритет P0–P3, точный файл и строки, сценарий воспроизведения, последствие и направление исправления. Не включай вкусовые предпочтения без практического последствия.
- Если замечаний нет, скажи об этом прямо. Кратко перечисли выполненные проверки и существенные непроверенные сценарии. Саморевью не называй независимым ревью другого разработчика или агента.
