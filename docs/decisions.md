# Технические решения

Документ описывает реализованную архитектуру Task Manager и причины её выбора. Команды запуска и настройки окружения находятся в [README](../README.md). Приложение проверено локально; публикация на Vercel и проверка опубликованной версии остаются следующим этапом.

## Архитектура приложения

Task Manager — один проект Next.js App Router с интерфейсом и серверным слоем. Серверные компоненты читают данные, Server Actions обрабатывают изменения. Такой вариант разрешён ТЗ и позволяет развёртывать приложение целиком. Отдельные HTTP endpoint-ы в `app/api` для этих сценариев не требуются.

Frontend использует облегчённый FSD с направлением зависимостей:

```text
app -> views -> widgets -> features -> entities -> shared
```

- `app` — маршруты, layouts, общие providers и глобальные стили. Страницы подключают конкретные views.
- `views` — композиция экранов; `widgets` — самостоятельные блоки, связывающие несколько действий пользователя.
- `features` — вход, создание, редактирование, удаление, поиск, фильтры и переключение темы.
- `entities` — модели списков и задач, доменные функции, общие поля формы и представления задач.
- `shared` — технические функции, конфигурация и общие UI-компоненты.

`src/server` находится вне цепочки frontend-слоёв и содержит сессии, подключение к PostgreSQL и операции с данными. Модули с доступом к базе и секретам защищены через `server-only`. Серверные действия feature экспортируются через `api/index.ts`, отдельно от её UI, чтобы клиентские импорты не подтягивали серверные модули.

Группы маршрутов `(auth)` и `(workspace)` разделяют страницу входа и рабочие страницы. Корневой layout подключает общие providers; workspace layout проверяет сессию и добавляет хедер. Клиентская граница расположена рядом с интерактивными компонентами.

## Данные и обновление интерфейса

Единственный источник списков и задач — PostgreSQL в Neon. Локальное состояние React содержит поля форм, открытые окна, выбранную задачу и фильтры. Чтение через RSC и изменения через Server Actions покрывают текущие сценарии, поэтому отдельное хранилище серверного кеша на клиенте не требуется.

Общая цепочка изменения:

```text
UI -> Server Action -> src/server -> PostgreSQL
```

Каждая защищённая операция самостоятельно проверяет сессию и внешние значения. Проверка layout и валидация Ant Design не заменяют серверные проверки. Значения передаются параметрами SQL. Ожидаемые ошибки возвращаются типизированным результатом; технические ошибки и служебные сигналы Next.js не перехватываются в слое данных. После успешной записи action вызывает `revalidatePath` для затронутых страниц. Мутации задач обновляют и `/lists/[id]`, и показатели `/lists`.

Для запросов используется `neon()` из `@neondatabase/serverless`: HTTPS подходит для выбранного serverless-размещения и не требует постоянного TCP-соединения. `getDb()` читает `DATABASE_URL` при обращении; импорт модуля сам по себе не подключается к базе. Для текущего объёма параметризованных SQL-запросов достаточно без ORM.

Начальная схема находится в `db/schema`. Команда `pnpm db:setup` выполняет SQL-файлы по имени в одной транзакции. Идентификаторы и даты создания задаёт PostgreSQL. Ограничения базы проверяют длину названий, статусы, приоритеты и конечный обязательный дедлайн. Внешний ключ связывает задачу со списком; `ON DELETE CASCADE` удаляет задачи вместе со списком. `IF NOT EXISTS` позволяет повторять инициализацию, но не обновляет существующие таблицы: изменение схемы потребует миграций.

Создание задачи использует `INSERT ... SELECT` из существующего списка. Редактирование и удаление ограничены одновременно UUID задачи и списка. Редактирование не меняет принадлежность и дату создания. Повторное удаление отсутствующей записи считается успешным, поэтому устаревшее состояние другой вкладки можно обновить без лишней ошибки.

Поиск списков выполняется на сервере по подстроке без учёта регистра через `strpos(lower(title), lower(query))`. Кавычки и символы `%` и `_` остаются обычным текстом. Запрос хранится в `q` URL и отправляется GET-формой Next.js, что сохраняет поиск при перезагрузке и переходах назад/вперёд. Порядок списков — `created_at DESC, id DESC`.

Статистика отображаемых списков загружается одним общим запросом задач после запроса списков. Отдельного запроса для каждой карточки нет; для расчёта читаются только `list_id`, `status` и `deadline`.

## Вход и сессия

Учётная запись из ТЗ — `admin@example.com` / `Admin123!`. Сервер проверяет демонстрационные данные без таблицы пользователей. Все посетители этой учётной записи работают с общими списками и задачами; регистрация и разделение данных по пользователям не предусмотрены.

Сессия — подписанный JWT через `jose` в HttpOnly cookie со сроком 8 часов, SameSite=Lax и Secure в production. При чтении проверяются подпись, алгоритм HS256, обязательные `sub` и `exp`, срок действия и идентификатор demo-пользователя. `SESSION_SECRET` задаётся через окружение и содержит минимум 32 символа. Пароль в токен не включается.

Выход удаляет cookie текущего браузера. Серверного списка отозванных токенов нет. Появление нескольких пользователей или требования отзыва сессий потребует пересмотра этого решения.

## Интерфейс и тема

Общие providers находятся в `app/providers`: один `AntdRegistry` добавляет серверные стили, `ThemeProvider` управляет выбранной темой, а `AntdProvider` подключает тему, русскую локализацию и контекст Ant Design. Приложение и Storybook используют одинаковое окружение.

`next-themes` сохраняет выбор «Светлая / Тёмная / Системная» в localStorage и отслеживает тему ОС в системном режиме. Собственные стили используют CSS-переменные; Ant Design — светлый и тёмный алгоритмы с разными ключами `cssVar`, чтобы стили модальных окон соответствовали текущей теме. До гидратации используется согласованное начальное состояние, а переключатель отключён. `useHydrated` задаёт эту границу через `useSyncExternalStore`.

`shared/ui/button` — общая обёртка над Ant Design Button со стандартными props, ref и оформлением из темы. `loading`, включая задержку индикатора, сразу блокирует кнопку и задаёт `aria-busy`. В остальное время сохраняется исходный `disabled`, включая наследование из Form. Бизнес-действия остаются в features. Встроенные кнопки footer Modal управляются штатными props Ant Design.

Карточка задачи открывается модальным окном: этот вариант разрешён ТЗ и сохраняет контекст списка. `TaskListTasks` хранит выбранный ID и получает задачу из актуальных серверных props; отдельный запрос при открытии не нужен. `TaskFormFields` переиспользуется при создании и редактировании. Отмена отбрасывает черновик; ошибка сохраняет ввод и позволяет повторить отправку. Во время мутации повторная отправка и закрытие окна заблокированы. Удаление требует подтверждения, для списка явно указано удаление всех его задач.

Фильтры статуса, приоритета и просрочки применяются совместно к уже загруженным задачам. Они локальны для страницы и сбрасываются при перезагрузке. После мутации данные перечитываются с сохранением выбранных условий. Изменение фильтров возвращает таблицу на первую страницу; счётчик показанных строк отличается от общего количества задач. Кнопки сброса поиска и фильтров видны постоянно и отключаются, когда сбрасывать нечего.

Таблица показывает по 10 строк. На узком экране горизонтально прокручивается таблица; поля форм, карточки и календарь адаптируются к ширине экрана.

## Правила задач и времени

Статусы — `new`, `in_progress`, `done`; приоритеты — `low`, `medium`, `high`. `overdue` — вычисляемый признак незавершённой задачи с дедлайном строго раньше текущего момента. Просроченная задача учитывается и в основном статусе, и в счётчике просрочки; выполненная задача просроченной не считается.

Дедлайн обязателен и содержит дату и время. Форма работает с местным временем браузера и передаёт UTC ISO timestamp. Сервер проверяет каноническое конечное значение, исключая несуществующие даты; прошедшие дедлайны разрешены. В PostgreSQL используется `timestamptz`. Таблица после гидратации показывает местное время; начальный серверный и клиентский рендер используют UTC, чтобы избежать расхождений.

`sortTasks`, `filterTasks` и `getTaskStats` находятся в `entities/task`, не зависят от React или базы и получают текущее время явно. Правила:

- Сначала идут незавершённые просроченные задачи, затем остальные незавершённые, затем выполненные.
- В каждой группе порядок определяется дедлайном по возрастанию и приоритетом по убыванию. При равенстве сохраняется исходный порядок; выдача задач из БД стабилизирована через `created_at ASC, id ASC`. Сортировка не изменяет входной массив.
- Прогресс — округлённый процент выполненных задач; для пустого списка — 0.
- Красный индикатор означает наличие просрочки и имеет преимущество перед жёлтым. Жёлтый означает дедлайн незавершённой задачи в интервале от текущего момента до 48 часов включительно. Иначе индикатор нейтральный. Цвет индикатора не определяет цвет полосы прогресса.

Показатели отражают момент серверного чтения. Фонового таймера нет: новое чтение пересчитывает сроки. Фильтры не изменяют общие показатели списка.

## Ошибки и проверки

Специальные файлы `loading.tsx` и `error.tsx` подключены в соответствующих сегментах маршрута; их UI находится во views. Ошибка загрузки позволяет повторить чтение на текущем URL. Неверный UUID или отсутствующий список вызывает `notFound()` и показывает экран «Список не найден».

Vitest разделён на три проекта:

- `unit` — доменные правила, валидация и серверные операции с подменёнными зависимостями. Для временных границ используется фиксированное время.
- `storybook` — взаимодействия с компонентами через `play` в Chromium: вход, валидация, смена статуса, создание, редактирование, удаление, поиск, фильтры, тема и общая кнопка. Истории используют контролируемые обработчики; успешный mock не доказывает сохранение в базе.
- `database` — отдельный запуск на настоящем PostgreSQL: сохранение, чтение, ограничения, связи, каскадное удаление и пересчёт статистики. Подменяется только сессия; собственные тестовые записи очищаются после прогона.

Тесты и истории расположены рядом с соответствующим кодом. `src/stories/antd.stories.tsx` проверяет инфраструктуру. Минимум ТЗ по юнит-тестам сортировки/счётчиков и продуктовым `play`-историям покрыт отдельными сценариями.

В Storybook 10 инструменты interaction tests импортируются из `storybook/test`; это API установленной версии вместо указанного в ТЗ `@storybook/test`. Браузерные тесты выполняются последовательно: при параллельной загрузке наблюдались нестабильные ошибки импорта до запуска сценариев.

## Размещение

Для публикации выбран Vercel, база PostgreSQL уже размещена в Neon. Серверные компоненты и Server Actions выполняются в окружении приложения; строки подключения и ключ сессии остаются серверными переменными окружения.

Node.js ограничен диапазоном `^22.12.0`: разрешены обновления внутри ветки 22, начиная с 22.12.0. Версия pnpm закреплена как `pnpm@11.19.0` в `packageManager`. На Vercel включается `ENABLE_EXPERIMENTAL_COREPACK=1`, чтобы сборка использовала эту версию менеджера пакетов. Установка зависимостей определяется автоматически, команда сборки — `pnpm build`.

На Vercel нужны `DATABASE_URL` и `SESSION_SECRET`. Файл `.env.local` используется локально и не хранится в Git; `.env.example` содержит только имена переменных. Начальная схема применяется отдельно командой `pnpm db:setup`, а сборка приложения не меняет базу. Постоянные данные хранятся в PostgreSQL.

После публикации нужно проверить вход, сохранение изменений, выход и темы на опубликованном адресе и добавить ссылку на demo в README. До этой проверки документ не утверждает готовность опубликованной версии.
