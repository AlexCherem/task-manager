# Технические решения

Здесь зафиксированы решения для тестового приложения. Выбранный подход не означает, что соответствующая функциональность уже реализована.

## Один проект Next.js

Используем Next.js App Router: интерфейс и небольшой серверный слой находятся в одном приложении. Серверные компоненты читают данные, Server Actions обрабатывают изменения. Это соответствует разрешённому в задании способу работы с данными и позволяет обойтись одним развёртываемым приложением.

Прямое чтение и запись в базу, а также работа с сессиями будут находиться в `src/server`. В серверных операциях должны проверяться сессия и входные данные. Данные форм и открытие модальных окон остаются локальным состоянием интерфейса.

## Облегчённый FSD

Используем знакомое по Service Cycle направление зависимостей:

```text
app -> views -> widgets -> features -> entities -> shared
```

`app` отвечает за Next.js и подключение приложения; `views` компонует экраны; `widgets` содержит крупные блоки; `features` — действия пользователя; `entities` — бизнес-модели и логику; `shared` — технический код. Серверная часть `src/server` выделена отдельно от этой цепочки.

Слои и slices добавляем вместе с функциональностью. TanStack Query пока не подключаем: исходный подход к чтению и изменениям опирается на серверные возможности Next.js.

## Хранение и размещение

Для demo выбраны Vercel Hobby и PostgreSQL в Neon Free с учётом лимитов бесплатных тарифов. Vercel размещает приложение и серверные функции; Neon хранит списки и задачи. Строка подключения доступна только серверному коду.

На момент первого коммита внешние сервисы ещё не подключены. Локальный файл базы на Vercel не используем как постоянное хранилище.

## Ant Design и карточка задачи

Ant Design разрешён заданием: UI-kit и стилизация оставлены на выбор разработчика. Тема и русская локализация общие для приложения и Storybook. Провайдеры собраны в `app/providers`: `AppProviders` подключает `AntdRegistry`, затем `ThemeProvider`, внутри которого `AntdProvider` читает выбранную тему и настраивает Ant Design. Корневой layout подключает только `AppProviders`. Один `AntdRegistry` добавляет стили при серверном рендеринге.

Карточку задачи планируем реализовать модальным окном. Такой вариант прямо разрешён заданием и позволяет просматривать и редактировать задачу в контексте её списка.

## Проверки

Vitest разделён на проекты `unit` и `storybook`. Чистая бизнес-логика тестируется в Node.js, истории и `play`-сценарии — в Chromium через Playwright. Продуктовые истории и тесты будут находиться рядом с соответствующими компонентами и функциями.

В ТЗ указан `@storybook/test`, но этот пакет относится к Storybook 8. В установленном Storybook 10 используем `storybook/test`, как описано в [актуальной документации](https://storybook.js.org/docs/writing-tests/interaction-testing). Проверки через `play` сохраняют требуемое поведение.

Начальная история кнопки проверяет инфраструктуру. Она не заменяет требуемые сценарии входа, валидации и смены статуса. Минимум восемь юнит-тестов сортировки/счётчиков и пять продуктовых `play`-историй остаются критериями готовности приложения.

## Правила задач

Дедлайн обязателен и содержит дату и время. При сохранении используем ISO 8601 в UTC; ввод и отображение в интерфейсе будут учитывать местное время пользователя. Доменные функции получают валидный timestamp с явным часовым поясом и сравнивают моменты времени без округления до календарного дня. Валидация входных данных относится к будущему серверному слою.

Основные статусы: `new`, `in_progress`, `done`. Приоритеты: `low`, `medium`, `high`. `overdue` — вычисляемый признак незавершённой задачи с дедлайном строго раньше текущего момента. Такая задача одновременно учитывается в счётчике основного статуса и в счётчике просроченных; завершённые задачи не считаются просроченными.

Порядок сортировки: незавершённые просроченные, остальные незавершённые, выполненные. В каждой группе задачи сортируются по возрастанию дедлайна, затем по убыванию приоритета. При полном совпадении критериев сохраняется исходный порядок. Сортировка возвращает новый массив.

Прогресс равен округлённому до целого проценту выполненных задач; для пустого списка он равен 0. Индикатор `overdue` отображается красным и имеет преимущество перед `due_soon`, который отображается жёлтым. `due_soon` означает наличие незавершённой задачи с дедлайном в интервале от текущего момента до 48 часов включительно. При отсутствии таких задач индикатор равен `none`.

Текущее время передаётся в `sortTasks` и `getTaskStats` явно, поэтому обе функции могут использовать один момент времени, а тесты не зависят от времени запуска. Эти функции и модель находятся в `entities/task` и не зависят от React или базы данных. Для дальнейшего ввода и проверки дат нужно использовать те же правила.

Поведение удаления списка с его задачами будет определено при реализации модуля списков.

## Вход и сессия

Для заданной в ТЗ учётной записи `admin@example.com` / `Admin123!` проверка выполняется на сервере без базы данных. Регистрацию и управление пользователями не добавляем. Клиентская форма валидирует поля, серверное действие повторно проверяет типы, наличие и длину входных значений перед прямым сравнением строк с демонстрационными email и паролем.

Используем подписанный JWT через `jose` в HttpOnly cookie. В payload записываются идентификатор пользователя (`sub`) и срок действия (`exp`); при чтении проверяются подпись, алгоритм HS256, наличие обоих полей, срок действия и идентификатор пользователя. Дополнительные issuer/audience и время выпуска для единственного приложения не задаём. Сессия действует 8 часов, SameSite=Lax, Secure включён в production. Срок хранения cookie задаётся через Max-Age. Ключ `SESSION_SECRET` хранится в переменных окружения и должен содержать минимум 32 символа. Токен подписан, но не зашифрован; пароль в него не включается.

`/lists` проверяет сессию на сервере. Удаление cookie при выходе завершает сессию в текущем браузере. Это stateless-сессия: серверного списка отозванных токенов нет; при появлении нескольких пользователей или требования отзыва сессий подход нужно пересмотреть.

Форма не зависит от Next.js навигации и cookie: она получает асинхронный обработчик через props. Это позволяет проверять её в Storybook. Серверные действия доступны через отдельный публичный вход `features/auth/api/index.ts` (реализация в `api/actions.ts`), чтобы импорт формы не подтягивал серверные зависимости в клиентский код.

## Хедер и тема

Хедер находится в `widgets/app-header` и подключается через серверный layout группы `(workspace)`. Layout получает пользователя из проверенной сессии. Проверки сессии в будущих операциях чтения и изменения данных остаются обязательными: layout может сохраняться между переходами и не заменяет защиту слоя данных.

Переключатель темы — отдельное действие пользователя в `features/theme`. `next-themes` отвечает за хранение выбора в localStorage, синхронизацию между вкладками и отслеживание системной темы. Начальный режим — `system`; атрибут `data-theme` корневого HTML-элемента определяет CSS-переменные собственных стилей. Для Ant Design используем штатные светлый и тёмный алгоритмы.

Сервер не знает содержимое localStorage и тему ОС. Поэтому первый React-рендер использует одинаковое начальное состояние на сервере и в браузере; после гидратации применяются пользовательские настройки. Небольшой общий хук `useHydrated` использует серверный и клиентский snapshots `useSyncExternalStore` для этой границы в provider и переключателе. Пока браузер не готов, переключатель отключён. `suppressHydrationWarning` применяется только к `html`, атрибуты которого меняет скрипт `next-themes` до гидратации.
